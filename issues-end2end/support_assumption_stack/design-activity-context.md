# 设计活动上下文：支持假设栈（嵌套的假设上下文）

## 1. 需求概述

### 1.1 问题背景
基于需求澄清文档分析，当前假设推理系统使用扁平假设池（`Context.assumptions: list[ABTree]`），在支持嵌套假设上下文方面存在以下局限性：

1. **缺乏嵌套支持**：无法表示"在假设A的基础上再假设B"的嵌套结构
2. **作用域不清晰**：所有假设在同一层级，无法区分不同上下文中的假设
3. **管理不灵活**：不能临时创建假设上下文然后恢复外层状态
4. **结论依赖不明确**：基于内层假设得出的结论在外层上下文中的状态不清晰

### 1.2 澄清的解决方案方向
需求澄清阶段确定了以下方向：
- **数据结构**：改为栈结构 `list[ABTree]`，每层一个假设
- **栈操作**：支持 `push`（创建新层）和 `pop`（弹出当前层）
- **可见性规则**：内层可以访问所有外层假设
- **向后兼容**：现有`assume`和`conclude`命令在单层上下文中行为不变

### 1.3 已确认的设计目标
需求澄清文档中明确的期望能力：
1. 支持嵌套假设上下文
2. 外层假设在内层作为公理可用
3. 灵活的假设生命周期管理
4. 明确的假设和结论作用域
5. 向后兼容现有`assume`和`conclude`命令

## 4. 涉及数据模型

### 4.1 当前数据模型状态（As-Is）

#### 4.1.1 假设池 (Assumption Pool)
```python
# context.py:86 观察到的代码
self.assumptions: list[ABTree] = []
```

**观察到的特征**：
- 扁平列表数据结构
- 所有假设在同一作用域
- 通过整数索引访问（0-based）
- 假设归结时从列表中移除选定假设
- `qed()`操作清空整个列表

#### 4.1.2 结论列表 (Conclusions)
```python
# context.py 中观察到的
self.conclusions: list[ABTree] = []
```

**观察到的特征**：
- 包含所有推导出的结论
- 当前不记录结论与假设的依赖关系
- 假设归结后，基于假设得出的结论仍然保留

### 4.2 目标数据模型要求（基于需求澄清）

#### 4.2.1 假设栈要求
- 数据结构：`list[ABTree]`（语义上作为栈使用）
- 每层一个假设
- 栈顶为当前活动层
- 内层可以访问所有外层假设
- 栈索引：0=栈底，依次递增

#### 4.2.2 已知的数据管理需求
1. **结论依赖关系**：需要记录结论与假设层的依赖关系
2. **清理机制**：`pop`时需要清理基于该层假设的结论
3. **状态跟踪**：可能需要跟踪当前栈深度等信息

#### 4.2.3 待解决的数据问题
1. 如何高效记录结论与假设层的依赖关系？
2. 如何设计数据结构以支持`pop`时的结论清理？
3. 是否需要扩展Context状态来管理栈信息？

## 5. 涉及业务逻辑机制和时序

### 5.1 当前业务逻辑流程观察

#### 5.1.1 假设声明流程（当前）
```
用户输入"assume P" → Switcher.switch() → Context.assume() → assumptions列表添加
```

#### 5.1.2 假设使用流程（当前）
```
/use API → LogicApi.use() → Context.assumptions[index]获取 → 添加到结论列表
```

#### 5.1.3 假设归结流程（当前）
```
/conclude API → LogicApi.conclude() → Context.conclude_start()过滤假设 → TermConverter.conclude()构建蕴含式
```

### 5.2 栈操作时序要求（基于需求澄清）

#### 5.2.1 push操作预期流程
```
预期：用户请求 → API端点 → 创建新假设层 → 外层假设在新层中可见
```

#### 5.2.2 pop操作预期流程
```
预期：用户请求 → API端点 → 识别基于当前层假设的结论 → 清理这些结论 → 弹出当前层
```

### 5.3 已知的时序约束（需求澄清中确定）

1. **模式约束**：栈操作必须在证明模式(`Proof`)下进行
2. **栈状态约束**：`pop`操作要求栈非空
3. **引用约束**：假设引用索引必须在有效范围内（0 ≤ 索引 < 当前栈深度）
4. **归结约束**：`conclude`只能归结当前层的假设
5. **生命周期约束**：`qed`操作清空整个栈

### 5.4 跨层引用机制观察
- **当前机制**：通过整数索引引用假设
- **栈适配需求**：需要支持通过栈索引引用任何可见层的假设
- **可见性规则**：内层可以引用外层（0到当前层-1），外层不能引用内层

## 6. 相关概念

### 6.1 核心概念定义（基于需求澄清）

#### 假设栈 (Assumption Stack)
- **澄清的定义**：嵌套的假设上下文数据结构，每层一个假设
- **特征**：后进先出(LIFO)，内层可访问外层，外层不可访问内层
- **表示**：`list[ABTree]`，索引0为栈底

#### 可见性规则 (Visibility Rules)
- **澄清的规则**：内层可以看到所有外层假设
- **引用语义**：使用外层假设相当于将其作为公理引入当前上下文

#### 结论依赖 (Conclusion Dependency)
- **澄清的需求**：需要记录结论与假设层的依赖关系
- **清理规则**：`pop`时清理所有基于该层假设的结论

#### 下标索引 (Stack Indexing)
- **澄清的方式**：通过整数下标引用假设层
- **规则**：0表示栈底，依次递增，当前层索引=栈深度-1

### 6.2 相关系统概念观察

#### 证明模式 (Proof Mode)
- 当前系统有三种模式：`Proof`、`Assert`、`Global`
- 需求澄清确认：假设栈只在`Proof`模式下有效

#### 语法树 (ABTree)
- 观察：假设和结论的统一表示形式
- 约束：需要保持ABTree结构兼容性

#### 蕴含式生成 (Implication Generation)
- 观察：通过`TermConverter.conclude()`实现
- 栈结构影响：只影响假设选择范围，不影响生成逻辑

## 8. Q&A（设计阶段待考虑问题）

### 8.1 数据管理问题

#### [1] 结论依赖关系的实现方式
**背景观察**：需要在`pop`时清理基于该层假设的结论，但当前系统不记录结论依赖关系。

**已知选项**（从技术角度观察）：
- 在结论中添加元数据记录依赖的假设层
- 维护外部映射表记录依赖关系
- 基于添加时间顺序管理依赖

**设计考虑因素**：
- 对现有数据结构的影响
- 实现复杂度
- 维护一致性难度

---

#### [2] 环境读取API的栈信息表示
**背景观察**：当前`/read` API返回扁平假设列表，需要扩展以支持栈结构显示。

**已知挑战**：
- 向后兼容性需求
- 信息完整性与格式简洁性的平衡
- 客户端期望的格式

**可能的表示方式观察**：
- 扩展现有`AS`项的格式
- 新增专门的栈信息项
- 保持现有格式，通过其他方式提供信息

---

### 8.2 系统行为问题

#### [3] 假设栈深度管理
**背景观察**：理论上栈深度无限制，但实际实现可能需要考虑限制。

**技术考虑因素**：
- 内存使用影响
- 用户体验考虑
- 错误处理需求

**可能的策略观察**：
- 不设硬性限制
- 设置合理上限
- 提供配置选项

---

#### [4] assume命令与push操作的关系
**背景观察**：需求澄清指出`assume`和`push`功能等价，`assume`是历史版本实现。

**需要明确的行为**：
- 空栈时`assume`的行为
- 栈非空时`assume`的行为
- `push`带term参数与不带参数的行为差异

---

#### [5] 错误处理机制
**背景观察**：栈操作引入新的错误场景，当前系统的错误处理机制需要扩展。

**新错误场景识别**：
- 非证明模式下调用栈操作
- 空栈时调用`pop`
- 越界的假设引用
- 无效的栈操作参数

**错误处理需求**：
- 清晰的错误响应
- 环境状态一致性保持
- 用户体验考虑

---

#### [6] 跨组件协作机制
**背景观察**：栈操作涉及多个组件协作，需要明确的调用链和数据流。

**协作点识别**：
- API端点与业务逻辑层的接口
- 业务逻辑层与Context的状态更新
- 结论依赖管理的组件责任划分
