# 支持假设栈设计分析

## 1. 组件和依赖

### 1.1 核心组件分析

#### Context类 (`semantic/context.py`)
- **职责**: 推理上下文状态管理（假设、结论、模式）
- **当前状态**: `assumptions: list[ABTree]`（扁平池）
- **目标状态**: 栈结构 `list[ABTree]`，每层一个假设
- **修改点**: 数据结构变更 + 栈操作逻辑 + 结论依赖管理

#### LogicApi类 (`semantic/logic_api.py`)
- **职责**: 业务逻辑入口（`/use`, `/conclude`处理）
- **修改点**: 适应栈索引引用 + 新增栈操作业务逻辑

#### logic_flask.py (`interface/logic_flask.py`)
- **职责**: HTTP API端点定义
- **修改点**: 新增 `/manage_assumption` 端点

#### 语法层组件（保持兼容）
- **Switcher** (`line.py`): 处理`assume`命令，保持现有行为
- **TermConverter** (`convert.py`): 蕴含式生成，适配栈过滤逻辑

## 5. 核心算法

### 5.1 栈索引解析伪代码

```python
def resolve_stack_index(user_index: int, stack_depth: int) -> int:
    """
    解析用户提供的栈索引

    参数:
        user_index: 用户输入的索引 (0-based)
        stack_depth: 当前栈深度

    返回:
        实际的栈层索引

    异常:
        IndexError: 索引超出范围 [0, stack_depth)
    """
    if not (0 <= user_index < stack_depth):
        raise IndexError(
            f"栈索引 {user_index} 超出范围 [0, {stack_depth})"
        )
    return user_index  # 直接映射（栈索引=下标索引）
```

### 5.2 依赖关系管理算法（简化版）

#### 结论添加时的依赖记录
```python
def record_conclusion_dependency(
    conclusion_id: int,
    stack_top_index: int,  # 结论推导时的栈顶层索引
    deps: Dict[int, int]   # 依赖映射表 {结论ID: 栈顶层索引}
) -> None:
    """
    记录结论对假设栈状态的依赖关系

    根据用户反馈简化：结论只依赖其推导时的栈顶层索引，
    表示依赖整个栈状态（以栈顶为标志）
    """
    deps[conclusion_id] = stack_top_index
```

#### `pop` 时的依赖清理
```python
def clean_layer_dependencies(
    layer_index: int,           # 要移除的层索引
    conclusion_deps: Dict[int, int],  # 依赖映射表 {结论ID: 栈顶层索引}
    conclusion_list: List[ABTree]     # 结论列表
) -> List[int]:
    """
    清理基于指定层及更深层的所有结论

    规则：清理所有依赖层索引 ≥ layer_index 的结论
    因为这些结论依赖的栈状态包含了要移除的层
    """
    to_remove = []

    # 识别依赖该层及更深层的结论
    for cid, dep_layer_index in conclusion_deps.items():
        if dep_layer_index >= layer_index:
            to_remove.append(cid)

    # 从映射表和列表中移除
    for cid in to_remove:
        conclusion_deps.pop(cid, None)
        # 从结论列表中移除（假设有ID到位置的映射）

    return to_remove
```

## 7. DFX设计

### 7.1 可扩展性设计

#### 设计原则
根据用户反馈，假设栈操作暂时不需要考虑扩展，因为后续可能改为树型假设域，届时将进行大规模重构。当前实现保持简单。

#### 当前设计特点
1. **数据结构简单**: 使用`list[ABTree]`表示栈，无额外抽象层
2. **操作最小化**: 仅实现`push`、`pop`核心操作
3. **无扩展预留**: 不预留扩展点，避免过度设计

#### 后续演进考虑
- 如需改为树型假设域，将重新设计数据结构
- 当前栈结构作为过渡实现，保持简单可靠

### 7.3 性能设计

#### 时间复杂度分析
| 操作 | 时间复杂度 | 数据量 | 优化措施 |
|------|-----------|--------|----------|
| `push` | O(1) | 栈深度 | 列表追加 |
| `pop` | O(k) | 依赖结论数k | 高效映射表 |
| 依赖查询 | O(1) | 结论数 | 哈希映射 |
| *可见性检查已移除* | - | - | - |

#### 内存使用优化
- **栈存储**: 每层一个ABTree，无额外开销
- **依赖映射**: 使用`Dict[int, int]`（结论ID → 栈顶层索引），内存最小
- **结论列表**: 保持现有结构，添加ID映射

## 8. Q&A（设计分析问题）

### 8.1 关键设计决策问题

#### Q1: 结论依赖映射的具体实现方案？
**需求澄清结论**: `pop`时要清理基于该层假设的结论。
**用户反馈**: 结论对假设的依赖，只要记录最近的就行了，也就是得出结论时的假设栈顶。

**设计决策**:
采用简化的外部映射表方案，只记录结论推导时的栈顶层索引。

**具体设计**:
- 数据结构: `Dict[int, int]` (结论ID → 栈顶层索引)
- 记录时机: 结论推导时记录当前栈顶索引
- 清理规则: `pop`时清理所有依赖层索引 ≥ 当前层索引的结论

**决策理由**:
1. 符合用户反馈的简化要求（只记录最近栈顶）
2. 保持ABTree接口不变
3. 实现简单，维护成本低
4. 内存开销最小（每个结论只存储一个整数）

#### Q2: `/read` API的栈信息表示方式？
**用户反馈**: 原有接口已经可以查看假设栈，无需修改。

**设计决策**:
保持现有`/read` API接口不变，栈结构通过假设列表的顺序自然表示。

**具体说明**:
- 现有`/read` API返回的假设列表(`AS`项)即为栈结构
- 列表顺序表示栈结构：索引0=栈底，最后一项=栈顶
- 栈深度 = 假设列表长度
- 当前层索引 = 栈深度-1

**决策理由**:
1. **完全兼容**: 不修改现有接口，确保零兼容性风险
2. **自然表示**: 栈结构通过列表顺序自然表达，无需额外字段
3. **简化实现**: 无需修改`Context.read()`方法和API响应格式

#### Q3: `assume`命令在栈上下文中的具体语义？
**需求澄清结论**: `assume`与`push`功能等价，`assume`是历史版本。

**需要明确的细节**:
1. 空栈时 `assume P` → 应执行 `push(P)` 还是报错？
2. 非空栈时 `assume Q` → 应覆盖当前层还是创建新层？
3. 多参数 `assume` 如何处理？

**设计决策**:
- `assume`命令始终是新增假设，在栈上下文中等价于`push`
- 空栈时: `assume P` ≡ `push(P)`（创建层0）
- 非空栈时: `assume Q` ≡ `push(Q)`（创建新层）
- 保持与历史版本语义一致：assume总是添加新假设

#### Q4: 错误处理的状态回滚机制？
**用户反馈**: 暂时不考虑，也不在需求范围内。

**设计决策**:
采用简单错误处理机制，不实现复杂的原子性保证。

**具体说明**:
- 保持与现有系统一致的错误处理方式
- 栈操作失败时可能遗留部分状态，但实际使用中风险可控
- 后续如有需要可再增强错误处理机制

**理由**:
1. 简化初始实现，聚焦核心功能
2. 现有系统错误处理已能满足基本需求
3. 符合用户反馈的简化要求

#### Q5: 栈深度是否有实际限制？
**用户反馈**: 暂时不考虑。

**设计决策**:
不设栈深度限制，采用最简单的实现方式。

**具体说明**:
- 栈深度无限制，依赖Python列表的天然容量
- 不实现额外的监控和配置机制
- 实际使用中栈深度通常很小，无需过度设计

**理由**:
1. 简化实现，避免不必要的复杂性
2. 符合用户反馈的简化要求
3. 实际场景中栈深度限制不是关键问题

#### Q6: 测试覆盖的充分性标准？
